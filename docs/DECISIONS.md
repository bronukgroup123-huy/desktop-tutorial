## ADR-001: Гостьовий режим — Supabase Anonymous Sign-In

**Рішення.** Гість входить через `supabase.auth.signInAnonymously()` і отримує реальний
UUID у `auth.users` (`is_anonymous = true`). Рядок у `public.users` створює той самий
тригер `handle_new_user()`. При реєстрації (Google / телефон / Apple) викликається
`linkIdentity` / `updateUser` — **UUID не змінюється**, міграції даних немає.

**SQLite на клієнті** — тільки кеш (каталог, прогнози, геометрія області) та офлайн-черга.
SQLite **не є** джерелом істини для даних гостя.

**Наслідки для бекенду:**
- Увімкнути Anonymous Sign-Ins у Supabase Auth; CAPTCHA (Turnstile) на анонімний вхід
  проти масового створення акаунтів; cron-очищення анонімних акаунтів без активності > 90 днів.
- RLS: анонімний користувач (`(auth.jwt() ->> 'is_anonymous')::boolean = true`) **не може**
  створювати `public`/`friends` точки, сесії Наглядача та SOS, додавати друзів.
  Сервер відповідає `403 registration_required` з `message`.
- Гість має Home Region (`PATCH /me`) — RegionGuard працює однаково для всіх.
- `GET /me` віддає `is_guest: true` і `onboarding.next_step`.

**Відкинуто:** суто локальний гостьовий режим у SQLite — потребував би міграції даних
при реєстрації і дублював би бізнес-логіку на клієнті.

## ADR-002: Фото тук-тука — Signed Upload URL

**Рішення.** Base64 у JSON заборонено. Потік створення точки:

1. Клієнт (онлайн або при синхронізації черги) → `POST v1-picks/upload-url`
   `{ client_id, content_type, size_bytes }` → сервер повертає `{ upload_url, path, expires_at }`
   (Supabase Storage `createSignedUploadUrl`, шлях `<user_id>/<client_id>.<ext>`).
2. Клієнт робить `PUT` файлу прямо в Storage (стрімінг з диска, без завантаження в пам'ять).
3. Клієнт → `POST v1-picks` `{ client_id, path, lat, lng, captured_at, visibility, ... }`.
4. Сервер читає файл зі Storage, перевіряє magic bytes, розмір, EXIF (GPS ≤ 1 км, час ≤ 24 год
   від `captured_at`), вирізає EXIF (перезапис об'єкта), створює запис.

**Офлайн-черга** зберігає тільки шлях до локального файлу та метадані. Повтори безпечні:
`client_id` — ключ ідемпотентності для обох кроків.

**Наслідки:** bucket `mushroom-photos` — політика Storage дозволяє INSERT тільки у
`<auth.uid()>/…`; незавершені завантаження (файл без запису `mushroom_picks` > 24 год)
видаляє cron. Старий `POST /picks` (base64) лишається для веб-прототипу до його виведення.

## ADR-003: Мінна небезпека — статичний банер без полігонів

**Рішення.** Офіційних машинозчитуваних даних немає, тому **жодних саморобних полігонів,
шарів чи попереджень у прогнозі**. Тільки статичний банер у вкладці «Безпека» з посиланням
на офіційні ресурси ДСНС.

**Наслідки:** таблиця `hazard_zones`, ендпоінт `v1-hazards` і блокування тук-туків у зонах
**не реалізуються**. Текст банера і посилання — у `GET v1-app-config` (`safety_notices`),
щоб змінювати їх без релізу застосунку. Перегляд рішення — коли з'являться офіційні
відкриті дані (новий ADR).

## ADR-004: WAF — без custom domain на MVP

**Рішення.** MVP: вбудований захист Supabase (платформний rate limit, JWT, RLS) +
наш IP rate limit у Edge Functions + безкоштовний Cloudflare перед Vercel (PWA Наглядача).
Custom domain для Supabase не купуємо.

**Наслідки:** весь захист API — на рівні коду: `_shared/rate-limit.ts` на кожному `v1-*`,
CAPTCHA для анонімного входу та OTP, ліміти на auth. CSP та HSTS — у `vercel.json` /
`next.config.mjs`. Перегляд — після релізу при зростанні навантаження або атаках.

## ADR-005: Оплата — RevenueCat

**Рішення.** Підписки Pro (сезонний, річний, сімейний) — через RevenueCat
(`purchases_flutter`). Власний білінг і пряму перевірку чеків Google Play не пишемо.

**Наслідки для бекенду:**
- `app_user_id` у RevenueCat = Supabase UUID (працює і для гостя завдяки ADR-001;
  після реєстрації UUID той самий).
- Edge Function `v1-revenuecat-webhook`: перевірка `Authorization`-секрету вебхука
  (Vault), ідемпотентність за `event.id`, оновлення таблиці `entitlements`.
- Джерело істини для доступу — `entitlements` у нашій БД; `GET /me` віддає
  `is_pro` і `features[]`. Клієнт не вирішує доступ за даними SDK RevenueCat.

## ADR-006: Розпізнавання — тільки локальний ONNX, без сервера

**Рішення.** Серверного розпізнавання немає. Використовується виключно локальна
квантована ONNX-модель BioCLIP 2 (~300 МБ).

- **Доставка моделі:** Play Asset Delivery (рекомендовано, fast-follow / on-demand pack);
  запасний варіант — завантаження при першому запуску (`dio` / `flutter_downloader`)
  з перевіркою `sha256` з `GET v1-models/manifest`.
- **Помилка інференсу** (Out of Memory тощо) → сервіс повертає `localFailure`, UI пропонує
  перейти в офлайн-довідник (326 видів) для ручного пошуку.
- **Жодних запитів на сервер для розпізнавання** — фото не залишають пристрій.

**Наслідки для бекенду:**
- Бекенд постачає лише **дані**: модель (manifest / Storage), каталог, двійників,
  правила безпечної подачі результату — через `v1-catalog/sync` для офлайн-SQLite.
- **Свідомий виняток із Thin Client:** правило «якщо серед top-3 є отруйний вид → червоний
  банер» виконується на клієнті, бо розпізнавання офлайн. Щоб логіка не хардкодилась,
  сервер віддає в каталозі для кожного виду `danger_level`, `danger_banner_label`,
  `twins[]`, а також глобальні тексти дисклеймера; клієнт лише застосовує їх.
- Ендпоінт `v1-recognize/*` не створюється.
- Ліміт «10 розпізнавань/день» для базової версії та «точніша модель для Pro» — див.
  відкриті питання в `BACKEND_PLAN.md` (розділ 6), бо без сервера їх не можна
  надійно контролювати.
