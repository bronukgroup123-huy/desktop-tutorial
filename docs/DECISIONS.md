## ADR-001: Гостьовий режим — Supabase Anonymous Sign-In

**Рішення.** Гість входить через `supabase.auth.signInAnonymously()` і отримує реальний
UUID у `auth.users` (`is_anonymous = true`). Рядок у `public.users` створює той самий
тригер `handle_new_user()`. При реєстрації (Google / телефон / Apple) викликається
`linkIdentity` / `updateUser` — **UUID не змінюється**, міграції даних немає.

**SQLite на клієнті** — тільки кеш (каталог, прогнози, геометрія області) та офлайн-черга.
SQLite **не є** джерелом істини для даних гостя.

**Наслідки для бекенду:**
- Увімкнути Anonymous Sign-Ins у Supabase Auth; CAPTCHA (Turnstile) на анонімний вхід
  проти масового створення акаунтів; cron-очищення анонімних акаунтів без активності > 90 днів.
- RLS: анонімний користувач (`(auth.jwt() ->> 'is_anonymous')::boolean = true`) **не може**
  створювати `public`/`friends` точки, сесії Наглядача та SOS, додавати друзів.
  Сервер відповідає `403 registration_required` з `message`.
- Гість має Home Region (`PATCH /me`) — RegionGuard працює однаково для всіх.
- `GET /me` віддає `is_guest: true` і `onboarding.next_step`.

**Відкинуто:** суто локальний гостьовий режим у SQLite — потребував би міграції даних
при реєстрації і дублював би бізнес-логіку на клієнті.

## ADR-002: Фото тук-тука — Signed Upload URL

**Рішення.** Base64 у JSON заборонено. Потік створення точки:

1. Клієнт (онлайн або при синхронізації черги) → `POST v1-picks/upload-url`
   `{ client_id, content_type, size_bytes }` → сервер повертає `{ upload_url, path, expires_at }`
   (Supabase Storage `createSignedUploadUrl`, шлях `<user_id>/<client_id>.<ext>`).
2. Клієнт робить `PUT` файлу прямо в Storage (стрімінг з диска, без завантаження в пам'ять).
3. Клієнт → `POST v1-picks` `{ client_id, path, lat, lng, captured_at, visibility, ... }`.
4. Сервер читає файл зі Storage, перевіряє magic bytes, розмір, EXIF (GPS ≤ 1 км, час ≤ 24 год
   від `captured_at`), вирізає EXIF (перезапис об'єкта), створює запис.

**Офлайн-черга** зберігає тільки шлях до локального файлу та метадані. Повтори безпечні:
`client_id` — ключ ідемпотентності для обох кроків.

**Наслідки:** bucket `mushroom-photos` — політика Storage дозволяє INSERT тільки у
`<auth.uid()>/…`; незавершені завантаження (файл без запису `mushroom_picks` > 24 год)
видаляє cron. Старий `POST /picks` (base64) лишається для веб-прототипу до його виведення.

## ADR-003: Мінна небезпека — статичний банер без полігонів

**Рішення.** Офіційних машинозчитуваних даних немає, тому **жодних саморобних полігонів,
шарів чи попереджень у прогнозі**. Тільки статичний банер у вкладці «Безпека» з посиланням
на офіційні ресурси ДСНС.

**Наслідки:** таблиця `hazard_zones`, ендпоінт `v1-hazards` і блокування тук-туків у зонах
**не реалізуються**. Текст банера і посилання — у `GET v1-app-config` (`safety_notices`),
щоб змінювати їх без релізу застосунку. Перегляд рішення — коли з'являться офіційні
відкриті дані (новий ADR).

## ADR-004: WAF — без custom domain на MVP

**Рішення.** MVP: вбудований захист Supabase (платформний rate limit, JWT, RLS) +
наш IP rate limit у Edge Functions + безкоштовний Cloudflare перед Vercel (PWA Наглядача).
Custom domain для Supabase не купуємо.

**Наслідки:** весь захист API — на рівні коду: `_shared/rate-limit.ts` на кожному `v1-*`,
CAPTCHA для анонімного входу та OTP, ліміти на auth. CSP та HSTS — у `vercel.json` /
`next.config.mjs`. Перегляд — після релізу при зростанні навантаження або атаках.

## ADR-005: Оплата — RevenueCat

**Рішення.** Підписки Pro (сезонний, річний; сімейного тарифу немає — ADR-010) — через RevenueCat
(`purchases_flutter`). Власний білінг і пряму перевірку чеків Google Play не пишемо.

**Наслідки для бекенду:**
- `app_user_id` у RevenueCat = Supabase UUID (працює і для гостя завдяки ADR-001;
  після реєстрації UUID той самий).
- Edge Function `v1-revenuecat-webhook`: перевірка `Authorization`-секрету вебхука
  (Vault), ідемпотентність за `event.id`, оновлення таблиці `entitlements`.
- Джерело істини для доступу — `entitlements` у нашій БД; `GET /me` віддає
  `is_pro` і `features[]`. Клієнт не вирішує доступ за даними SDK RevenueCat.

## ADR-006: Розпізнавання — тільки локальний ONNX, без сервера

**Рішення.** Серверного розпізнавання немає. Використовується виключно локальна
квантована ONNX-модель BioCLIP 2 (~300 МБ).

- **Доставка моделі:** Play Asset Delivery (рекомендовано, fast-follow / on-demand pack);
  запасний варіант — завантаження при першому запуску (`dio` / `flutter_downloader`)
  з перевіркою `sha256` з `GET v1-models/manifest`.
- **Помилка інференсу** (Out of Memory тощо) → сервіс повертає `localFailure`, UI пропонує
  перейти в офлайн-довідник (326 видів) для ручного пошуку.
- **Жодних запитів на сервер для розпізнавання** — фото не залишають пристрій
  (єдиний виняток — явна добровільна згода за ADR-009).

**Наслідки для бекенду:**
- Бекенд постачає лише **дані**: модель (manifest / Storage), каталог, двійників,
  правила безпечної подачі результату — через `v1-catalog/sync` для офлайн-SQLite.
- **Свідомий виняток із Thin Client:** правило «якщо серед top-3 є отруйний вид → червоний
  банер» виконується на клієнті, бо розпізнавання офлайн. Щоб логіка не хардкодилась,
  сервер віддає в каталозі для кожного виду `danger_level`, `danger_banner_label`,
  `twins[]`, а також глобальні тексти дисклеймера; клієнт лише застосовує їх.
- Ендпоінт `v1-recognize/*` не створюється.
- Ліміти та Pro-модель — вирішено в ADR-007 і ADR-008.

## ADR-007: Розпізнавання без лімітів

**Рішення.** Ліміт «10 розпізнавань/день» прибрано повністю. Локальний інференс нам
нічого не коштує, а штучні обмеження дратують. **«Безлімітне безкоштовне офлайн-розпізнавання»**
— головний маркетинговий аргумент безкоштовної версії.

**Наслідки:** жодних лічильників ні на сервері, ні на клієнті; таблиця `recognition_usage`
не створюється; розпізнавання відсутнє в `features[]` Pro.

## ADR-008: Одна модель ШІ, Pro без AI-переваг

**Рішення.** Підтримуємо **одну** ONNX-модель для всіх. Пункт «точніша модель для Pro»
прибрано з опису підписки (дві моделі — зайвий технічний борг).

**Pro не містить жодних AI-переваг.** Повний склад безкоштовної версії та Pro —
у [ADR-010](#adr-010-безкоштовна-версія-vs-pro) (замінює попередній перелік у цьому ADR).

**Наслідки:** `v1-models/manifest` віддає одну модель для всіх без перевірки `features[]`;
один asset pack у Play Asset Delivery.

## ADR-009: Фото для навчання ШІ — тільки opt-in

**Рішення.** За замовчуванням фото **нікуди не відправляються**. Після успішного
розпізнавання UI показує кнопку **«Допомогти покращити ШІ? Надіслати фото анонімно для
навчання»**. Тільки після натискання фото завантажується в окремий приватний bucket
`training_data`. ML-пайплайнів зараз не будуємо — лише збираємо датасет для майбутнього
fine-tuning.

**Як забезпечується анонімність:**
- Клієнт перед відправкою зменшує фото (довга сторона ≤ 1024 px) і вирізає EXIF.
  Сервер повторно вирізає EXIF (не довіряємо клієнту).
- Шлях у bucket не містить `user_id`: `training_data/<model_version>/<uuid>.jpg`.
- Метадані — тільки те, що потрібно для навчання: `model_version`, top-3 передбачення
  (id видів + ранг), `user_label` (якщо користувач уточнив вид), місяць зйомки.
  **Без координат, без точного часу, без ідентифікатора користувача.**
- Rate limit на відправку (захист від спаму) рахується окремо від записів датасету,
  тому запис неможливо зв'язати з користувачем.

**Згода:** кожне натискання кнопки — окрема згода на конкретне фото. Текст біля кнопки
чесно попереджає: фото анонімне, тому відкликати його згодом неможливо. Загальний перемикач
«Ніколи не пропонувати» — у Налаштуваннях (зберігається локально).

**Наслідки для бекенду:** bucket `training_data` (приватний, читання — тільки
service_role); `POST v1-training/upload-url` → PUT у Storage → `POST v1-training/submit`
(та ж схема, що ADR-002); таблиця `training_samples`; cron видаляє непідтверджені
завантаження старше 24 год. Доступно і гостям (ADR-001).

## ADR-010: Безкоштовна версія vs Pro

**Принцип.** Безкоштовна версія — повноцінний безпечний похід: SOS, один Наглядач,
живий трек для Наглядача, компас назад, безлімітне офлайн-розпізнавання, офлайн-довідник,
прогноз на найближчі дні. Pro продає **глибину аналітики, розширену безпеку для родини,
архів і статус**. Ми ніколи не обмежуємо те, що потрібно для порятунку в лісі.

### 10.2 Рейтинг і Pro

Замінено ADR-013 §13.4. Було: **Лісовик — знижка 20% на Pro**, **Грибний Майстер — Pro
безкоштовно** (видається як `entitlements.source = 'rating'`, без RevenueCat).

### 10.3 Технічні наслідки

- Сервер віддає в `GET /me` перелік `features[]`; клієнт показує/ховає функції **тільки**
  за ним. Ключі: `forecast_extended`, `heatmap_all_ukraine`, `heatmap_history`,
  `offline_regions_unlimited`, `guardians_3`, `gpx_tracks`, `badge_premium`,
  `expert_chats`, `no_ads`, `picks_pro_limit`.
- Обмеження перевіряє **сервер** (горизонт прогнозу, bbox/період теплової карти,
  кількість Наглядачів у сесії, доступ до GPX-ендпоінтів). Клієнтська перевірка — тільки для UI.
- Безкоштовний користувач отримує на Pro-ендпоінт `403 pro_required` з `message`
  (текст для пейвола).

### 10.4 Уточнення Product Owner (2026-11-09)

1. **GPX** — підтверджено: живий трек для Наглядача і компас назад безкоштовні;
   файл GPX і архів треків — тільки Pro.
2. **Теплова карта** — з рівня Лісовик (безкоштовно, своя область, актуальна) або в Pro
   (вся Україна + історія до 30 днів).
3. **Публічні точки** — безкоштовно тільки з рівня Лісовик, до 5 на добу; у Pro — з будь-якого
   рівня, від 5 на добу і більше за рейтингом. Приватні точки — див. ADR-011.
4. **Сімейний тариф прибрано.** Лишаються сезонний і річний Pro.

### 10.5 Наслідок, який треба врахувати в рейтингу

Безкоштовний Мандрівник і Слідопит не публікують точок, тому бали рейтингу **не можуть
залежати тільки від verified публічних точок** — інакше безкоштовний користувач ніколи не
дійде до Лісовика (201 бал). Потрібні інші джерела балів (див. `BACKEND_PLAN.md`, розділ 6).

## ADR-011: Ліміт приватних точок

**Рішення.** У безкоштовній версії приватні точки обмежені: **до 5 на добу**, доступні
з будь-якого рівня (рівень Лісовик не потрібен). Гість (ADR-001) — той самий ліміт.
У Pro приватні точки — без ліміту.

**Наслідки:** перевірка в тій самій БД-функції, що й публічні (`can_create_pick`),
окремі лічильники для `private` і `public`; перевищення → `429 daily_limit_reached`.
Офлайн-черга: точки понад ліміт сервер відхиляє при синхронізації з тим самим кодом —
клієнт показує повідомлення з `message` і лишає точку в локальному щоденнику.

## ADR-012: Джерела балів рейтингу — тести знань

**Рішення.** Головне джерело балів для безкоштовних користувачів — **тести на знання грибів
і розуміння грибництва**. Вони навчають, роблять грибників усвідомленішими і безпечнішими,
і не потребують публічних точок.

**Правила (захист від «накрутки»):**
- Питання і правильні відповіді зберігаються **тільки на сервері**; клієнт отримує питання
  без відповідей, перевірка — на сервері (Thin Client). Бали — **тільки онлайн**;
  офлайн доступний режим тренування без балів.
- Кожна спроба — випадкова вибірка з банку питань модуля; бали за модуль нараховуються
  **один раз** (поріг проходження, напр. ≥ 80%). Повторне проходження — без балів.
- Сумарно тести дають обмежену частку шляху: **до ~120 балів** — достатньо, щоб навчанням
  дійти до Слідопита (51) і пройти більшу частину шляху до Лісовика (201). Решту дає
  реальна безпечна активність у лісі.
- Контент тестів (особливо про отруйні види й першу допомогу) **перевіряє міколог**
  перед публікацією.

**Фото в тестах:** фото є для **132 видів** — фото-питання будуються лише на них (і пари
двійників — лише якщо фото є в обох). Решта з 326 видів — текстові питання.

**Модулі першої хвилі:** «Отруйні двійники» (фото-питання на базі 132 видів з фото),
«Безпека в лісі», «Етика збору і Червона книга», «Перша допомога при отруєнні»,
«Сезони і хвилі», «Знавець виду» (короткі тести по ТОП-20).

**Рівень за тести:** проходження **всіх** модулів дає окремий рівень «Грибознавець»
(або позначку «Досвідчений» для вищих рівнів) — див. ADR-013.

**Інші джерела балів (затверджено всі 8):**

| # | Джерело | Бали | Ліміт |
|---|---|---|---|
| 1 | Сесія Наглядача завершена вчасно | +5 | 1/добу |
| 2 | Відповідь «Знайшли? Так/Ні» після походу | +2 | 1/добу, правила ADR-014 |
| 3 | Приватна точка з успішною EXIF-перевіркою | +1 | 5/добу |
| 4 | Підтвердження чужої публічної точки поруч (≥ Слідопит) | +3 | 3/добу |

| 6 | Сезонний челендж | +15 | за челендж |

Не нараховуємо: розпізнавання, фото для навчання ШІ (ADR-009), відкриття застосунку.

## ADR-013: Система рівнів (6 рівнів + сертифікат знань)

**Рішення.** Рейтинг має дві незалежні складові:
1. **Бали** (`users.rating`, сума ledger `rating_events`) — реальна активність.
2. **Сертифікат знань** (`users.knowledge_certified_at`) — видається, коли пройдено
   **всі** модулі тестів (ADR-012). Сертифікат не зникає, якщо пізніше додадуться нові
   модулі (фіксується версія програми `curriculum_version`).

### 13.1 Рівні

| # | Рівень | Як отримати | З сертифікатом знань |
|---|---|---|---|
| 1 | **Мандрівник** | 0–50 балів | — |
| 2 | **Слідопит** | 51–200 балів | → стає «Грибознавцем» |
| 3 | **Грибознавець** 🆕 | **тільки** сертифікат знань (усі тести) + ≥ 51 бал, < 201 бал. За бали цей рівень отримати неможливо | — |
| 4 | **Лісовик** | 201–500 балів | → **«Досвідчений лісовик»** |
| 5 | **Хранитель лісу** 🆕 | 501–1000 балів (тільки за бали) | → **«Досвідчений хранитель лісу»** |
| 6 | **Грибний Майстер** | 1001+ балів **і** сертифікат знань | (сертифікат обов'язковий) |

Приклади:
- Новачок пройшов усі тести (+120 балів) → **Грибознавець**: вище за Слідопита, але до
  Лісовика (201) треба ще реальна активність.
- Лісовик пройшов усі тести → **Досвідчений лісовик** (привілеї Лісовика + значок і
  бонуси сертифіката).
- 1001 бал без тестів → лишається **Хранителем лісу**, поки не пройде тести:
  Майстер має знати отруйних двійників.

### 13.2 Порядок рівнів для перевірок доступу

`Мандрівник < Слідопит < Грибознавець < Лісовик < Хранитель лісу < Грибний Майстер`.
«Досвідчений» — це не окремий щабель, а позначка `certified = true` на рівні.
Усі правила «з рівня Лісовик» (ADR-010) діють для Лісовика і вище, з позначкою чи без.

### 13.3 Технічні наслідки

- Таблиця-конфіг `rating_levels` (`code`, `min_points`, `max_points`,
  `requires_certificate`, `label`, `certified_label`, `privileges` JSONB) — пороги й назви
  змінюються без релізу.
- БД-функція `compute_level(rating, certified)` → `level_code`; `GET /me` віддає
  `level_code`, `level_label` (вже з «Досвідчений…»), `is_certified`, `next_level_label`,
  `next_level_hint` («Ще 81 бал до Лісовика» / «Пройдіть 2 тести, щоб стати Грибознавцем»).
- Клієнт не рахує рівні — тільки показує `level_label` (Thin Client).

### 13.4 Бонуси рейтингу і Pro (замінює ADR-010 §10.2)

- Лісовик — знижка 20% на Pro; Хранитель лісу — 30%.
- Грибний Майстер — Pro безкоштовно (`entitlements.source = 'rating'`).

### 13.5 Привілеї та ліміти рівнів (підтверджено PO 2026-11-09)

| Рівень | Безкоштовно | Pro |
|---|---|---|
| Грибознавець | привілеї Слідопита + значок «Грибознавець», вага його підтверджень чужих точок ×1.5; **публічні точки й теплова — ні** (з Лісовика, ADR-010) | публічні 20/добу |
| Лісовик | публічні 5/добу, теплова Home Region | публічні 50/добу |
| Хранитель лісу | публічні 10/добу, теплова Home Region + сусідні області, право позначати підозрілі точки для модерації | публічні 100/добу |
| Грибний Майстер | Pro безкоштовно, експертні прогнози | ∞ |
| «Досвідчений …» | значок сертифіката + вага підтверджень ×1.5 | те саме |

Публічні точки Pro для нижчих рівнів: Мандрівник 5 / Слідопит 20 (без змін).
Поріг Майстра піднято з 500+ до 1001+ — через появу Хранителя лісу.

## ADR-014: Чесний відгук «Знайшли?» — захист від спаму

**Рішення.** Бали за відповідь «Знайшли? Так / Ні» (+2, 1/добу) нараховуються, лише якщо
відповідь пов'язана з реальним походом, а сам користувач **розуміє, що чесна відповідь
працює на нього**.

### 14.1 Користувач бачить, що це для нього

- Перед питанням — коротке пояснення (текст із сервера): «Чим чесніша відповідь, тим
  точніший прогноз — передусім для вас: ваших лісів і вашої області. Неправдиві відповіді
  погіршують ваш власний прогноз».
- Це має бути **правдою**, а не лише текстом: відгуки впливають на **персональну
  точність** прогнозу користувача і на калібрування його області (`calibration_log`).
- У щоденнику — блок «Ваш прогноз»: «Прогноз для вас збувся 7 з 10 разів», «Ваші відгуки
  покращили прогноз для Київської області» — щоб користувач бачив результат своєї чесності.

### 14.2 Технічний захист від спаму

- Відгук приймається тільки для **конкретного походу**: завершена сесія Наглядача або
  прогноз, який користувач відкривав для цієї точки в цей день (`forecast_views`).
  Без такого зв'язку — `422 no_trip_context`, балів немає.
- Місце відгуку має збігатися з треком сесії або точкою прогнозу (≤ 5 км).
- Ліміт: 1 відгук з балами на добу; бали нараховуються **через 24 год** (час на перевірку).
- **Довіра** `users.feedback_trust` (0…1): падає, якщо відповіді суперечать власним
  перевіреним точкам користувача (наприклад, «нічого немає» в місці, де він того ж дня
  створив точку з EXIF). При довірі нижче порогу: бали не нараховуються, вага відгуку в
  калібруванні знижується. Користувачу показуємо м'яке нагадування, без звинувачень.
