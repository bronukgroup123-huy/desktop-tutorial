## ADR-001: Гостьовий режим — Supabase Anonymous Sign-In

**Рішення.** Гість входить через `supabase.auth.signInAnonymously()` і отримує реальний
UUID у `auth.users` (`is_anonymous = true`). Рядок у `public.users` створює той самий
тригер `handle_new_user()`. При реєстрації (Google / телефон / Apple) викликається
`linkIdentity` / `updateUser` — **UUID не змінюється**, міграції даних немає.

**SQLite на клієнті** — тільки кеш (каталог, прогнози, геометрія області) та офлайн-черга.
SQLite **не є** джерелом істини для даних гостя.

**Наслідки для бекенду:**
- Увімкнути Anonymous Sign-Ins у Supabase Auth; CAPTCHA (Turnstile) на анонімний вхід
  проти масового створення акаунтів; cron-очищення анонімних акаунтів без активності > 90 днів.
- RLS: анонімний користувач (`(auth.jwt() ->> 'is_anonymous')::boolean = true`) **не може**
  створювати `public` точки, сесії Наглядача та SOS. (Видимість `friends` і друзів
  скасовано — ADR-018.)
  Сервер відповідає `403 registration_required` з `message`.
- Гість має Home Region (`PATCH /me`) — RegionGuard працює однаково для всіх.
- `GET /me` віддає `is_guest: true` і `onboarding.next_step`.

**Відкинуто:** суто локальний гостьовий режим у SQLite — потребував би міграції даних
при реєстрації і дублював би бізнес-логіку на клієнті.

## ADR-002: Фото тук-тука — Signed Upload URL

**Рішення.** Base64 у JSON заборонено. Потік створення точки:

1. Клієнт (онлайн або при синхронізації черги) → `POST v1-picks/upload-url`
   `{ client_id, content_type, size_bytes }` → сервер повертає `{ upload_url, path, expires_at }`
   (Supabase Storage `createSignedUploadUrl`, шлях `<user_id>/<client_id>.<ext>`).
2. Клієнт робить `PUT` файлу прямо в Storage (стрімінг з диска, без завантаження в пам'ять).
3. Клієнт → `POST v1-picks` `{ client_id, path, lat, lng, captured_at, visibility, ... }`.
4. Сервер читає файл зі Storage, перевіряє magic bytes, розмір, EXIF (GPS ≤ 1 км, час ≤ 24 год
   від `captured_at`), вирізає EXIF (перезапис об'єкта), створює запис.

**Офлайн-черга** зберігає тільки шлях до локального файлу та метадані. Повтори безпечні:
`client_id` — ключ ідемпотентності для обох кроків.

**Наслідки:** bucket `mushroom-photos` — політика Storage дозволяє INSERT тільки у
`<auth.uid()>/…`; незавершені завантаження (файл без запису `mushroom_picks` > 24 год)
видаляє cron. Старий `POST /picks` (base64) лишається для веб-прототипу до його виведення.

## ADR-003: Мінна небезпека — статичний банер без полігонів

**Рішення.** Офіційних машинозчитуваних даних немає, тому **жодних саморобних полігонів,
шарів чи попереджень у прогнозі**. Тільки статичний банер у вкладці «Безпека» з посиланням
на офіційні ресурси ДСНС.

**Наслідки:** таблиця `hazard_zones`, ендпоінт `v1-hazards` і блокування тук-туків у зонах
**не реалізуються**. Текст банера і посилання — у `GET v1-app-config` (`safety_notices`),
щоб змінювати їх без релізу застосунку. Перегляд рішення — коли з'являться офіційні
відкриті дані (новий ADR).

## ADR-004: WAF — без custom domain на MVP

**Рішення.** MVP: вбудований захист Supabase (платформний rate limit, JWT, RLS) +
наш IP rate limit у Edge Functions + безкоштовний Cloudflare перед Vercel (PWA Наглядача).
Custom domain для Supabase не купуємо.

**Наслідки:** весь захист API — на рівні коду: `_shared/rate-limit.ts` на кожному `v1-*`,
CAPTCHA для анонімного входу та OTP, ліміти на auth. CSP та HSTS — у `vercel.json` /
`next.config.mjs`. Перегляд — після релізу при зростанні навантаження або атаках.

## ADR-005: Оплата — RevenueCat

**Рішення.** Підписки Pro (сезонний, річний; сімейного тарифу немає — ADR-010) — через RevenueCat
(`purchases_flutter`). Власний білінг і пряму перевірку чеків Google Play не пишемо.

**Наслідки для бекенду:**
- `app_user_id` у RevenueCat = Supabase UUID (працює і для гостя завдяки ADR-001;
  після реєстрації UUID той самий).
- Edge Function `v1-revenuecat-webhook`: перевірка `Authorization`-секрету вебхука
  (Vault), ідемпотентність за `event.id`, оновлення таблиці `entitlements`.
- Джерело істини для доступу — `entitlements` у нашій БД; `GET /me` віддає
  `is_pro` і `features[]`. Клієнт не вирішує доступ за даними SDK RevenueCat.

## ADR-006: Розпізнавання — тільки локальний ONNX, без сервера

**Рішення.** Серверного розпізнавання немає. Використовується виключно локальна
квантована ONNX-модель BioCLIP 2 (~300 МБ).

- **Доставка моделі:** Play Asset Delivery (рекомендовано, fast-follow / on-demand pack);
  запасний варіант — завантаження при першому запуску (`dio` / `flutter_downloader`)
  з перевіркою `sha256` з `GET v1-models/manifest`.
- **Помилка інференсу** (Out of Memory тощо) → сервіс повертає `localFailure`, UI пропонує
  перейти в офлайн-довідник (326 видів) для ручного пошуку.
- **Жодних запитів на сервер для розпізнавання** — фото не залишають пристрій
  (єдиний виняток — явна добровільна згода за ADR-009).

**Наслідки для бекенду:**
- Бекенд постачає лише **дані**: модель (manifest / Storage), каталог, двійників,
  правила безпечної подачі результату — через `v1-catalog/sync` для офлайн-SQLite.
- **Свідомий виняток із Thin Client:** правило «якщо серед top-3 є отруйний вид → червоний
  банер» виконується на клієнті, бо розпізнавання офлайн. Щоб логіка не хардкодилась,
  сервер віддає в каталозі для кожного виду `danger_level`, `danger_banner_label`,
  `twins[]`, а також глобальні тексти дисклеймера; клієнт лише застосовує їх.
- Ендпоінт `v1-recognize/*` не створюється.
- Ліміти та Pro-модель — вирішено в ADR-007 і ADR-008.

## ADR-007: Розпізнавання без лімітів

**Рішення.** Ліміт «10 розпізнавань/день» прибрано повністю. Локальний інференс нам
нічого не коштує, а штучні обмеження дратують. **«Безлімітне безкоштовне офлайн-розпізнавання»**
— головний маркетинговий аргумент безкоштовної версії.

**Наслідки:** жодних лічильників ні на сервері, ні на клієнті; таблиця `recognition_usage`
не створюється; розпізнавання відсутнє в `features[]` Pro.

## ADR-008: Одна модель ШІ, Pro без AI-переваг

**Рішення.** Підтримуємо **одну** ONNX-модель для всіх. Пункт «точніша модель для Pro»
прибрано з опису підписки (дві моделі — зайвий технічний борг).

**Pro не містить жодних AI-переваг.** Повний склад безкоштовної версії та Pro —
у [ADR-010](#adr-010-безкоштовна-версія-vs-pro) (замінює попередній перелік у цьому ADR).

**Наслідки:** `v1-models/manifest` віддає одну модель для всіх без перевірки `features[]`;
один asset pack у Play Asset Delivery.

## ADR-009: Фото для навчання ШІ — тільки opt-in

**Рішення.** За замовчуванням фото **нікуди не відправляються**. Після успішного
розпізнавання UI показує кнопку **«Допомогти покращити ШІ? Надіслати фото анонімно для
навчання»**. Тільки після натискання фото завантажується в окремий приватний bucket
`training_data`. ML-пайплайнів зараз не будуємо — лише збираємо датасет для майбутнього
fine-tuning.

**Як забезпечується анонімність:**
- Клієнт перед відправкою зменшує фото (довга сторона ≤ 1024 px) і вирізає EXIF.
  Сервер повторно вирізає EXIF (не довіряємо клієнту).
- Шлях у bucket не містить `user_id`: `training_data/<model_version>/<uuid>.jpg`.
- Метадані — тільки те, що потрібно для навчання: `model_version`, top-3 передбачення
  (id видів + ранг), `user_label` (якщо користувач уточнив вид), місяць зйомки.
  **Без координат, без точного часу, без ідентифікатора користувача.**
- Rate limit на відправку (захист від спаму) рахується окремо від записів датасету,
  тому запис неможливо зв'язати з користувачем.

**Згода:** кожне натискання кнопки — окрема згода на конкретне фото. Текст біля кнопки
чесно попереджає: фото анонімне, тому відкликати його згодом неможливо. Загальний перемикач
«Ніколи не пропонувати» — у Налаштуваннях (зберігається локально).

**Наслідки для бекенду:** bucket `training_data` (приватний, читання — тільки
service_role); `POST v1-training/upload-url` → PUT у Storage → `POST v1-training/submit`
(та ж схема, що ADR-002); таблиця `training_samples`; cron видаляє непідтверджені
завантаження старше 24 год. Доступно і гостям (ADR-001).

## ADR-010: Безкоштовна версія vs Pro

**Принцип.** Безкоштовна версія — повноцінний безпечний похід: SOS, один Наглядач,
живий трек для Наглядача, компас назад, безлімітне офлайн-розпізнавання, офлайн-довідник,
прогноз на найближчі дні. Pro продає **глибину аналітики, розширену безпеку для родини,
архів і статус**. Ми ніколи не обмежуємо те, що потрібно для порятунку в лісі.

### 10.2 Рейтинг і Pro

Замінено ADR-013 §13.4. Було: **Лісовик — знижка 20% на Pro**, **Грибний Майстер — Pro
безкоштовно** (видається як `entitlements.source = 'rating'`, без RevenueCat).

### 10.3 Технічні наслідки

- Сервер віддає в `GET /me` перелік `features[]`; клієнт показує/ховає функції **тільки**
  за ним. Ключі: `forecast_extended`, `analysis_pro` (ADR-015: 3 ділянки, 10×10, розширена погода), `map_all_ukraine` (лише перегляд),
  `heatmap_all_ukraine`, `heatmap_history`,
  `offline_ukraine_map`, `group_trips`, `region_change_once`, `guardians_3`, `gpx_tracks`, `badge_premium`,
  `expert_chats`, `no_ads`, `picks_pro_limit`.
- Обмеження перевіряє **сервер** (горизонт прогнозу, bbox/період теплової карти,
  кількість Наглядачів у сесії, доступ до GPX-ендпоінтів). Клієнтська перевірка — тільки для UI.
- Безкоштовний користувач отримує на Pro-ендпоінт `403 pro_required` з `message`
  (текст для пейвола).

### 10.4 Уточнення Product Owner (2026-11-09)

1. **GPX** — підтверджено: живий трек для Наглядача і компас назад безкоштовні;
   файл GPX і архів треків — тільки Pro.
2. **Теплова карта** — з рівня Лісовик (безкоштовно, своя область, актуальна) або в Pro
   (вся Україна + історія до 30 днів).
3. **Публічні точки** — безкоштовно тільки з рівня Лісовик, до 5 на добу; у Pro — з будь-якого
   рівня, від 5 на добу і більше за рейтингом. Приватні точки — див. ADR-011.
4. **Сімейний тариф прибрано.** Лишаються сезонний і річний Pro.

### 10.5 Наслідок, який треба врахувати в рейтингу

Безкоштовний Мандрівник і Слідопит не публікують точок, тому бали рейтингу **не можуть
залежати тільки від verified публічних точок** — інакше безкоштовний користувач ніколи не
дійде до Лісовика (201 бал). Потрібні інші джерела балів (див. `BACKEND_PLAN.md`, розділ 6).

## ADR-011: Ліміт приватних точок

**Рішення.** У безкоштовній версії приватні точки обмежені: **до 5 на добу**, доступні
з будь-якого рівня (рівень Лісовик не потрібен). Гість (ADR-001) — той самий ліміт.
У Pro приватні точки — без ліміту.

> **Змінено ADR-019 §19.10:** безкоштовно (і гість) — **до 5 приватних точок одночасно** (щоб
> додати нову — видалити стару), Pro — **до 15 одночасно**; нових — не більше 10 на тиждень. На
> сервері зберігається лише мініатюра фото приватної точки.

**Наслідки:** перевірка в тій самій БД-функції, що й публічні (`can_create_pick`),
окремі лічильники для `private` і `public`; перевищення → `429 daily_limit_reached`.
Офлайн-черга: точки понад ліміт сервер відхиляє при синхронізації з тим самим кодом —
клієнт показує повідомлення з `message` і лишає точку в локальному щоденнику.

## ADR-012: Джерела балів рейтингу — тести знань

**Рішення.** Головне джерело балів для безкоштовних користувачів — **тести на знання грибів
і розуміння грибництва**. Вони навчають, роблять грибників усвідомленішими і безпечнішими,
і не потребують публічних точок.

**Правила (захист від «накрутки»):**
- Питання і правильні відповіді зберігаються **тільки на сервері**; клієнт отримує питання
  без відповідей, перевірка — на сервері (Thin Client). Бали — **тільки онлайн**;
  офлайн доступний режим тренування без балів.
- Кожна спроба — випадкова вибірка з банку питань модуля; бали за модуль нараховуються
  **один раз** (поріг проходження, напр. ≥ 80%). Повторне проходження — без балів.
- Сумарно тести дають обмежену частку шляху: **до ~120 балів** — достатньо, щоб навчанням
  дійти до Слідопита (51) і пройти більшу частину шляху до Лісовика (201). Решту дає
  реальна безпечна активність у лісі.
- Контент тестів (особливо про отруйні види й першу допомогу) **перевіряє міколог**
  перед публікацією.

**Фото в тестах:** фото є для **132 видів** — фото-питання будуються лише на них (і пари
двійників — лише якщо фото є в обох). Решта з 326 видів — текстові питання.

**Модулі першої хвилі:** «Отруйні двійники» (фото-питання на базі 132 видів з фото),
«Безпека в лісі», «Етика збору і Червона книга», «Перша допомога при отруєнні»,
«Сезони і хвилі», «Знавець виду» (короткі тести по ТОП-20).

**Рівень за тести:** проходження **всіх** модулів дає окремий рівень «Грибознавець»
(або позначку «Досвідчений» для вищих рівнів) — див. ADR-013.

**Інші джерела балів (затверджено всі 8):**

| # | Джерело | Бали | Ліміт |
|---|---|---|---|
| 1 | Сесія Наглядача завершена вчасно | +5 | 1/добу |
| 2 | Відповідь «Знайшли? Так/Ні» після походу | +2 | 1/добу, правила ADR-014 |
| 3 | Приватна точка з успішною EXIF-перевіркою | +1 | 5/тиждень (ADR-019 §19.10) |
| 4 | Підтвердження чужої публічної точки поруч (≥ Слідопит) | +3 | 3/добу |
| 5 | Друг за запрошенням пройшов онбординг і перший похід | +10 | 5 за весь час |
| 6 | Сезонний челендж | +15 | за челендж |
| 7 | Виправлення в довіднику (після модерації) | +5 | — |
| 8 | Серія навчання 7 днів поспіль | +5 | 1/тиждень |

Автору публічної точки — **+2 за кожне підтвердження відповіддю, до 10 на добу** (ADR-019 §19.5).

Не нараховуємо: розпізнавання, фото для навчання ШІ (ADR-009), відкриття застосунку.

## ADR-013: Система рівнів (6 рівнів + сертифікат знань)

**Рішення.** Рейтинг має дві незалежні складові:
1. **Бали** (`users.rating`, сума ledger `rating_events`) — реальна активність.
2. **Сертифікат знань** (`users.knowledge_certified_at`) — видається, коли пройдено
   **всі** модулі тестів (ADR-012). Сертифікат не зникає, якщо пізніше додадуться нові
   модулі (фіксується версія програми `curriculum_version`).

### 13.1 Рівні

| # | Рівень | Як отримати | З сертифікатом знань |
|---|---|---|---|
| 1 | **Мандрівник** | 0–50 балів | — |
| 2 | **Слідопит** | 51–200 балів | → стає «Грибознавцем» |
| 3 | **Грибознавець** 🆕 | **тільки** сертифікат знань (усі тести) + ≥ 51 бал, < 201 бал. За бали цей рівень отримати неможливо | — |
| 4 | **Лісовик** | 201–500 балів | → **«Досвідчений лісовик»** |
| 5 | **Хранитель лісу** 🆕 | 501–1000 балів (тільки за бали) | → **«Досвідчений хранитель лісу»** |
| 6 | **Грибний Майстер** | 1001+ балів **і** сертифікат знань | (сертифікат обов'язковий) |

Приклади:
- Новачок пройшов усі тести (+120 балів) → **Грибознавець**: вище за Слідопита, але до
  Лісовика (201) треба ще реальна активність.
- Лісовик пройшов усі тести → **Досвідчений лісовик** (привілеї Лісовика + значок і
  бонуси сертифіката).
- 1001 бал без тестів → лишається **Хранителем лісу**, поки не пройде тести:
  Майстер має знати отруйних двійників.

### 13.2 Порядок рівнів для перевірок доступу

`Мандрівник < Слідопит < Грибознавець < Лісовик < Хранитель лісу < Грибний Майстер`.
«Досвідчений» — це не окремий щабель, а позначка `certified = true` на рівні.
Усі правила «з рівня Лісовик» (ADR-010) діють для Лісовика і вище, з позначкою чи без.

### 13.3 Технічні наслідки

- Таблиця-конфіг `rating_levels` (`code`, `min_points`, `max_points`,
  `requires_certificate`, `label`, `certified_label`, `privileges` JSONB) — пороги й назви
  змінюються без релізу.
- БД-функція `compute_level(rating, certified)` → `level_code`; `GET /me` віддає
  `level_code`, `level_label` (вже з «Досвідчений…»), `is_certified`, `next_level_label`,
  `next_level_hint` («Ще 81 бал до Лісовика» / «Пройдіть 2 тести, щоб стати Грибознавцем»).
- Клієнт не рахує рівні — тільки показує `level_label` (Thin Client).

### 13.4 Бонуси рейтингу і Pro (замінює ADR-010 §10.2)

- Лісовик — знижка 20% на Pro; Хранитель лісу — 30%.
- Грибний Майстер — Pro безкоштовно (`entitlements.source = 'rating'`).

### 13.5 Привілеї та ліміти рівнів (підтверджено PO 2026-11-09)

| Рівень | Безкоштовно | Pro |
|---|---|---|
| Грибознавець | привілеї Слідопита + значок «Грибознавець», вага його підтверджень чужих точок ×1.5; **публічні точки й теплова — ні** (з Лісовика, ADR-010) | публічні 20/добу |
| Лісовик | публічні 5/добу, теплова Home Region | публічні 50/добу |
| Хранитель лісу | публічні 10/добу, теплова Home Region + сусідні області, право позначати підозрілі точки для модерації | публічні 100/добу |
| Грибний Майстер | Pro безкоштовно, експертні прогнози | ∞ |
| «Досвідчений …» | значок сертифіката + вага підтверджень ×1.5 | те саме |

Публічні точки Pro для нижчих рівнів: Мандрівник 5 / Слідопит 20 (без змін).
Поріг Майстра піднято з 500+ до 1001+ — через появу Хранителя лісу.

> **Змінено ADR-019 §19.10:** безкоштовні ліміти публічних — **на тиждень**: Лісовик 7, Хранитель
> лісу 15 (відповіді-знахідки входять у ліміт). Ліміти Pro — окремим рішенням разом із B6.3.

## ADR-014: Чесний відгук «Знайшли?» — захист від спаму

**Рішення.** Бали за відповідь «Знайшли? Так / Ні» (+2, 1/добу) нараховуються, лише якщо
відповідь пов'язана з реальним походом, а сам користувач **розуміє, що чесна відповідь
працює на нього**.

### 14.1 Користувач бачить, що це для нього

- Перед питанням — коротке пояснення (текст із сервера): «Чим чесніша відповідь, тим
  точніший прогноз — передусім для вас: ваших лісів і вашої області. Неправдиві відповіді
  погіршують ваш власний прогноз».
- Це має бути **правдою**, а не лише текстом: відгуки впливають на **персональну
  точність** прогнозу користувача і на калібрування його області (`calibration_log`).
- У щоденнику — блок «Ваш прогноз»: «Прогноз для вас збувся 7 з 10 разів», «Ваші відгуки
  покращили прогноз для Київської області» — щоб користувач бачив результат своєї чесності.

### 14.2 Технічний захист від спаму

- Відгук приймається тільки для **конкретного походу**: завершена сесія Наглядача або
  прогноз, який користувач відкривав для цієї точки в цей день (`forecast_views`).
  Без такого зв'язку — `422 no_trip_context`, балів немає.
- Місце відгуку має збігатися з треком сесії або точкою прогнозу (≤ 5 км).
- Ліміт: 1 відгук з балами на добу; бали нараховуються **через 24 год** (час на перевірку).
- **Довіра** `users.feedback_trust` (0…1): падає, якщо відповіді суперечать власним
  перевіреним точкам користувача (наприклад, «нічого немає» в місці, де він того ж дня
  створив точку з EXIF). При довірі нижче порогу: бали не нараховуються, вага відгуку в
  калібруванні знижується. Користувачу показуємо м'яке нагадування, без звинувачень.

## ADR-015: Машинний прогноз (аналіз ділянок)

**Рішення.** Машинний прогноз — інструмент планування «куди варто поїхати»: користувач
ставить точку на карті, а рушій прогнозу аналізує **квадрат навколо неї** (погода, тип і вік
лісу, хвиля, умови для кожного виду). Результат — **тільки рівні** (Висока / Середня /
Низька / Недостатньо даних), **без відсотків** (маніфест, Заборона №1).

### 15.1 Безкоштовно vs Pro

| | Безкоштовно | Pro |
|---|---|---|
| Кількість ділянок | 1 | **до 3** одночасно, з порівнянням і ранжуванням на сервері |
| Розмір ділянки | 5×5 км | **5×5 або 10×10 км** (вибір користувача) |
| Де можна ставити | **тільки своя область (Home Region)** | **тільки своя область (Home Region)** |
| Горизонт | як звичайний прогноз: 3 дні | як звичайний прогноз: понад 10 днів (ADR-010) |
| Погода | базова: температура, вологість, опади | **розширена**: опади за 30 днів, вологість і температура ґрунту, графік температур, сума тепла (GDD), тренд тиску, дні після дощу |
| Карти аналізу | — | карта опадів за останні дні, вологості ґрунту, шар типів і віку лісу в ділянці |
| **Ліміт аналізів** | **5 на добу** | **10 на добу на кожну ділянку** (3 ділянки → 30 на добу) |

Порівняння 3 ділянок одним запитом списує по 1 аналізу з кожної ділянки.
Перевищення → `429 analysis_limit_reached` з `message` і часом скидання.

### 15.2 Карта і ділянки — тільки Home Region (уточнення PO 2026-11-09)

Простіше логічно і технічно:
- **Полігони лісів завантажуються тільки для області користувача** (Home Region) — і в
  безкоштовній версії, і в Pro.
- **Точки й ділянки аналізу ставляться тільки в межах своєї області** — і в безкоштовній
  версії, і в Pro. Сервер перевіряє це через RegionGuard (`403 outside_home_region`).
- Зміна Home Region — тільки Pro і тільки один раз (ADR-016): старі полігони видаляються з
  пристрою, підтягуються полігони й карта нової області; ділянки в старій області неактивні.
- **«Вся Україна»** (тільки Pro) — спрощені кордони областей, теплова карта всієї України
  (ADR-010) і **групові поїздки** (маршрут + нотатки, ADR-017). У цьому режимі **немає
  полігонів лісів і не можна ставити тук-туки, точки прогнозу чи ділянки аналізу** —
  маршрут і нотатки не є прогнозними точками.
- Сервер відмовляє в полігонах для bbox поза Home Region (`403 outside_home_region`) або
  більшого за область (`400 bbox_too_large`).

### 15.3 Технічні наслідки

- Таблиця `analysis_areas` (user_id, center, size_km 5/10, label, slot 1–3) — збережені
  ділянки; кількість слотів і розмір перевіряє сервер за `features[]`.
- Лічильник `analysis_usage` (user_id, **slot**, day, count) — ліміт на слот, див. §15.4.
- RegionGuard для аналізу: **тільки Home Region** для всіх (`403 outside_home_region`);
  `features.analysis_pro` дає лише кількість ділянок, розмір 10×10 і розширену погоду.
- Погода для ділянки — сітка точок (3×3 для 5×5 км, 5×5 для 10×10 км) одним запитом до
  Open-Meteo через `weather_cache` (B2.6); карти аналізу будуються з цієї ж сітки.

### 15.4 Ділянка незмінна; прогноз — тільки для ділянки (уточнення PO 2026-11-12)

1. **Тап по лісу на карті — лише визначник лісу.** На лісі з'являється підпис його типу
   (і віку, якщо відомий). Прогнозу для точки по тапу немає.
2. **Прогноз — тільки для ділянки аналізу.** Ділянку обирають на карті («Аналіз ділянки» →
   центр → розмір → «Створити ділянку й аналізувати»). Далі вся робота з нею — у вкладці
   «Прогноз»: результат, повторний аналіз, «Показати на карті», видалення.
3. **Змінити (пересунути) ділянку не можна.** Щоб обрати інше місце, стару ділянку видаляють
   і створюють нову. Pro — до 3 ділянок одночасно (§15.1); безкоштовно — одна.
4. **Ліміт аналізів — на слот за добу**, а не на ділянку: «видалити → створити» його не
   обнуляє (інакше видалення стало б обходом ліміту).
5. **Останній результат зберігається з ділянкою** (`last_result`) — вкладка «Прогноз»
   показує його без нового списання, на будь-якому пристрої; без інтернету — копія з телефону.
6. Ліс у ділянці рахує застосунок із тих самих полігонів, що на карті (файл лісів області),
   і передає серверу як `forest` — у БД сервера ліси є не для всіх областей.

API: `POST v1-analysis { lat, lng, size_km }` — нова ділянка (`409 area_limit_reached`, якщо
слоту немає); `POST v1-analysis { area_id }` — повторний аналіз; `DELETE v1-analysis/areas/{id}`.

### 15.5 Тип лісу: OSM, а де породи немає — супутник (рішення PO 2026-11-12)

Відкритого сервісу порід для України немає (Copernicus FTY і ForestPaths Україну не
покривають, шари Лісопроєкту закриті). У OSM порода вказана лише для ~5% лісів області.

1. **Полігони лісів лишаються** (межі й малі гаї — з OSM, файл області). Видаляти їх або
   переходити на сітку — окреме рішення після перевірки на карті.
2. **Тип полігона:** спершу OSM (порода → хвойний/листяний → назва урочища). Якщо в OSM
   типу немає — **за супутником**: середня ймовірність «хвойний» по полігону з карти 40 м
   (Sentinel-2 влітку й у безлистий період + ESA WorldCover, Random Forest на лісах OSM з
   породою): ≥ 60% — хвойний, ≤ 40% — листяний, між — мішаний. Лише ці три типи, без породи.
3. Джерело типу видно у визначнику (`type_source = satellite`, «Визначено за супутниковими
   знімками (Sentinel-2) — без породи»); з кількох контурів під пальцем OSM має перевагу.
4. Усе рахується заздалегідь у GitHub Actions (карта — реліз `forest-type-data`, тип — у
   файлі лісів області). Застосунок нічого не запитує в сторонніх сервісів.
5. Точність перевіряється на половині лісів OSM з породою, яку модель не бачила
   (Житомирщина, пілот: ≈ 90% хвойний/листяний на рівні пікселів).
6. **Запобіжник якості** (рішення PO 2026-11-13): карту області публікують лише якщо на лісах OSM,
   яких модель не бачила, точність хвойний/листяний ≥ 75% і перевірочних лісів досить (≥ 8 кожного
   класу). Інакше публікується лише звіт, а ліси області лишаються з типом з OSM. Карти рахуються
   для всіх областей разом (раз на рік) і після цього перезбираються файли лісів.
7. Ліси області без власної карти можуть отримати тип із карт **сусідніх областей**, що заходять на
   її край (Чернівецька 2026-11: свою карту не опубліковано — замало позначених хвойних лісів;
   ~58% лісів отримали тип із карт сусідніх Карпатських областей). Так і лишаємо.


### 15.6 Уточнення лісу ділянки вручну (рішення PO 2026-11-13)

1. У вкладці «Прогноз», у картці лісу ділянки — кнопка **«Уточнити ліс»**. Для кожного типу з
   карти («Хвойний ліс ≈ 16 км²») користувач обирає **1–2 породи зі списку** (сосна, ялина, дуб,
   береза, осика, вільха, граб, бук тощо) і може додати породу, якої карта не бачить («У ділянці
   ще є: дуб» — «переважає» / «є місцями»). **Лише вибір зі списку**, вільного тексту немає.
   Площі не вводяться — лишаються з карти.
2. **Не частіше 2 разів на добу на ділянку** (доба — за київським часом). Щоб змінити втретє —
   наступного дня.
3. Після збереження уточнення **сервер одразу переаналізує ділянку** з уточненими породами — у
   прогнозі з'являються відповідні гриби (напр. «сосна» → види, що ростуть під сосною). Такий
   переаналіз **не списує** добовий ліміт аналізів ділянки — його обмежує п. 2.
4. Уточнення зберігається **з ділянкою** (ділянку не пересувають — уточнення завжди про те саме
   місце) і видаляється разом із нею. У картці лісу видно джерело: «Хвойний ліс → сосна ·
   уточнено вами» і кнопка «Скинути до карти» (теж рахується як уточнення).
5. **На загальну карту лісів уточнення не впливає** і голосом за тип полігона не є: тип на карті
   змінюють лише перевірені тук-туки й відповіді на них (ADR-019 §19.4). У картці — підказка:
   «Знайдете тут гриб — зробіть тук-тук, і ліс уточниться для всіх».
6. API (Thin Client): `PUT v1-analysis/areas/{id}/forest { override: { types: [{ forest_type, species: [..] }],
   extra: [{ species, presence: dominant|present }] } | null, forest? }` (`null` — «Скинути до карти»;
   `forest` — ліс із карти, як у POST) → результат переаналізу + `forest_edit`; понад ліміт —
   `429 forest_edit_limit_reached` з `message` і `Retry-After`. Список порід (`forest_edit_options`),
   уточнення ділянки (`forest_override`) і залишок уточнень (`forest_edit`) — у `GET v1-analysis`.
7. Прогноз з уточненням рахується для до 3 порід: площа типу ділиться між обраними породами,
   «переважає» — першою, «є місцями» — після решти. Збережене уточнення діє і на кожен наступний
   аналіз ділянки.

## ADR-016: Зміна Home Region — тільки Pro і один раз

**Рішення.** Безкоштовний користувач не може змінити область після онбордингу.
У Pro область можна змінити **рівно один раз** за весь час існування акаунта.

### 16.1 Що відбувається при зміні
1. Сервер перевіряє `features.region_change_once` і що змін ще не було
   (`region_change_log`), інакше `403 region_change_not_allowed` з `message`.
2. `users.home_region_id` оновлюється, запис у `region_change_log` (старий/новий регіон,
   час, device fingerprint).
3. Клієнт **видаляє з пристрою** полігони лісів, офлайн-карту і кеш старої області
   й завантажує полігони та карту нової області.
4. Ділянки аналізу (ADR-015) у старій області стають неактивними; власні тук-туки і
   щоденник зберігаються (історія користувача), але нові точки — лише в новій області.
5. Якщо Pro закінчився — змінена область лишається; повторна зміна неможлива.

### 16.2 Технічні наслідки
- `PATCH /me { home_region_slug }` після завершення онбордингу проходить лише через цю
  перевірку; під час онбордингу (`home_region = null`) — вільний перший вибір.
- `GET /me` → `region_change: { allowed, reason_label }` — застосунок не вирішує сам.

### 16.3 Уточнення PO (2026-11-09)
1. **Помилка при онбордингу:** протягом **24 год** після першого вибору область можна
   змінити **безкоштовно один раз** (не зараховується як Pro-зміна).
2. **Переїзд безкоштовного користувача:** зміна можлива через **звернення в підтримку** з
   ручною перевіркою (запис у `region_change_log` з `source = 'support'`); у застосунку —
   тільки Pro.

## ADR-017: Групові поїздки: офлайн-карта України, маршрут і спільні нотатки

**Рішення.** Pro відкриває **офлайн-карту всієї України** для організації групових поїздок:
маршрут, малювання й нотатки на карті, які бачать і доповнюють усі учасники групи.

### 17.1 Можливості
- **Маршрут:** точки старту/фінішу, проміжні точки, лінія маршруту (у тому числі за межами
  Home Region — це планування поїздки, а не прогноз).
- **Малювання й нотатки:** обвести область чи об'єкт (полігон / коло), лінія, стрілка,
  мітка з підписом, текстова нотатка-нагадування. Колір і стиль — з палітри.
- Усе зберігається **разом із маршрутом** як одна «поїздка».
- **Групова поїздка:** учасники бачать маршрут і всі нотатки; можуть **дописувати й
  домальовувати** (за правами ролі). Видно автора кожного елемента.
- **Офлайн:** карта, маршрут і нотатки доступні без мережі; зміни офлайн стають у чергу і
  синхронізуються при появі зв'язку.

### 17.2 Межі (узгоджено з ADR-015)
- Полігони лісів на офлайн-карті України **не показуються** (лише Home Region).
- Прогноз, ділянки аналізу і тук-туки поза Home Region **недоступні**.
- Груповий режим безпеки (живі позиції, SOS) — окрема безкоштовна функція; поїздку можна
  пов'язати з сесією Наглядача.

### 17.3 Ролі
| Роль | Права |
|---|---|
| Власник (Pro, створює поїздку) | усе, включно з видаленням будь-яких елементів і учасників |
| Редактор | додає елементи, змінює і видаляє **свої** |
| Глядач | лише перегляд |

### 17.4 Технічні наслідки
- Таблиці: `trips` (owner, title, dates, status), `trip_members` (trip, user, role),
  `trip_features` (trip, author, kind: `route|waypoint|polygon|circle|line|arrow|label|note`,
  geometry, style, text, `version`, `deleted_at`, `client_id`).
- RLS: дані поїздки бачать **лише учасники**. Запрошення — за посиланням-кодом з терміном дії.
- Синхронізація: Supabase Realtime (канал на поїздку) онлайн; офлайн — черга з `client_id`
  (ідемпотентність, ADR-002); конфлікти — по елементу, «остання версія перемагає» за
  `version`; видалення — м'яке (`deleted_at`).
- **Тайли офлайн-карти:** публічні тайли OpenStreetMap **заборонено** масово завантажувати
  для офлайну (політика OSM). Потрібен власний векторний файл тайлів (PMTiles / MBTiles)
  у Storage або провайдер з дозволом на офлайн. Завантажуємо не всю Україну, а **коридор
  маршруту / обрані області** — щоб не займати гігабайти на телефоні.
- Ліміти: розмір групи, кількість елементів на поїздку, розмір тексту нотатки.

### 17.5 Чому це цінно
Груповий виїзд — найчастіший сценарій для сімей і компаній. Спільна карта з нотатками
(«тут паркуємось», «сюди не йти — болото», «зустріч о 14:00 біля дуба») робить застосунок
центром підготовки поїздки, а не лише інструментом у лісі. Це сильний аргумент для Pro.

### 17.6 Уточнення PO (2026-11-09)
1. **Учасники без Pro** приєднуються до поїздки Pro-власника як **редактори** (можуть
   дописувати й домальовувати). Створює поїздку тільки Pro.
2. **Розмір групи:** до **10 учасників**.
3. **Терміни: реалізуємо в MVP**, а не у v1.1 — щоб модель даних, синхронізація й офлайн
   закладались одразу і не довелось переробляти карту, групи безпеки та сесії Наглядача
   пізніше. Це «родзинка» продукту.
4. **Поширення точок (ADR-018, 2026-11-10).** Окремих «друзів» і точок `friends` немає.
   Ділитися своїми точками з людьми, з якими йдеш по гриби, можна **лише всередині
   групової поїздки** (§17.7).

### 17.7 Поширення точок у поїздці (ADR-018)
- Учасник може поширити **свою** приватну точку в поїздку: у `trip_features` з'являється
  елемент `kind = shared_pick` з посиланням на точку (фото, назва, опис, точні координати).
- Бачать її **лише учасники цієї поїздки**; сама точка лишається приватною і не з'являється
  на публічній карті. Автор може прибрати її з поїздки будь-коли.
- Вихід учасника з поїздки або видалення поїздки прибирає доступ до його поширених точок.

## ADR-018: Тук-тук: лише приватні й публічні точки, фото з камери, перевірка виду

**Дата:** 2026-11-10 · **Статус:** ✅ Прийнято · **Скасовує:** видимість `friends`, таблицю
друзів (`friendships`) і задачу B3.6.

### 18.1 Видимість точок
- Під час створення тук-тука — **лише дві видимості: `private` і `public`**.
- Окремої функції «друзі» немає. Поділитися точками з компанією — тільки через **групову
  поїздку** (ADR-017 §17.7).
- Хто може створювати `public` — без змін: ADR-010, ADR-011, ADR-013. Гість — лише
  `private` (ADR-001).

### 18.2 Карта
- Відкриваючи карту, користувач **одразу бачить публічні точки** інших (у Home Region):
  сірі — «Перевіряється», зелені — «Підтверджено».
- Перемикач **«Приватні точки»**: показує власні приватні точки, і кнопка «Тук-тук» стає
  **«Приватний тук-тук»**.
- Якщо користувачу ще не можна створювати публічні точки (рівень / ліміт), кнопка одразу
  «Приватний тук-тук», поруч — підказка з сервера, як відкрити публічні (`*_label`).
- Тап по публічній точці → Bottom Sheet: фото, назва, опис, дата, статус перевірки,
  кнопка «Поскаржитися» і застереження «Фото користувача — не порада їсти гриб».

### 18.3 Створення тук-тука
1. Натискання «Тук-тук» відкриває **камеру застосунку**. **Галереї немає**, знімок —
   **один** (можна перезняти до відправлення).
2. Координати й час фіксуються пристроєм у момент зйомки. Точка поза Home Region —
   не створюється (ADR-015 §15.2).
3. **Назва — тільки зі списку видів довідника** (з пошуком). Варіант **«Не знаю, що це»**
   дозволений, але така точка може бути **лише приватною**.
4. **Опис** — необов'язковий, вільний текст (під якими деревами, погода). Обмеження
   довжини; телефони, посилання і контакти відфільтровуються.
5. Відправлення — Signed Upload URL (ADR-002); без мережі — офлайн-черга з `client_id`.

### 18.4 Перевірка «фото відповідає назві» — три шари
**Шар 1 — розпізнавання на телефоні (ADR-006, ADR-007).** Одразу після знімка локальна
модель ONNX:
- **«Не гриб»** → публікувати не можна (лише перезняти).
- Вид збігається з вибраною назвою → позначка «Збігається з розпізнаванням».
- Модель бачить **отруйного двійника** вибраного виду (`species_twins.danger`) → червоне
  попередження; публічна точка отримує прапорець `twin_alert` і **ніколи не
  підтверджується автоматично**.
- Результат передається на сервер як **підказка** (`ai_check`: версія моделі, top-класи
  рівнями без відсотків, `match`, `twin_alert`). Підробити його можна, тому це **не доказ**.
  Сервер ШІ не запускає (ADR-006); фото для навчання — лише opt-in (ADR-009).

**Шар 2 — підтвердження спільнотою (B3.8).**
> **Замінено ADR-019 §19.5:** окремої групи перевіряльників немає. Публічна точка одразу сіра на
> карті й стає підтвердженою, коли Лісовик відповів на неї своєю перевіреною знахідкою. Текст
> нижче — історія рішення.

- Нова публічна точка — `pending` («Перевіряється»).
- Перевіряти можуть користувачі **із сертифікатом знань і рівнем від «Грибознавець»**
  (ADR-013), не автор. Стрічка «Перевірити»: фото + назва → «Так» / «Ні» / «Це інший вид».
- **3 «Так»** (з вагами рівнів ADR-013) → `verified`; переважання «Ні» / «Інший вид» →
  `rejected`, точка зникає з публічної карти, автору −20 балів (ADR-012/B3.7).
  Перевіряльник отримує бали, якщо його голос збігся з підсумком (з добовим лімітом).
- Для небезпечних видів і точок з `twin_alert` — **тільки люди**, автопідтвердження немає
  навіть для довірених авторів.

**Шар 3 — довіра й скарги.**
- Автор з історією підтверджених точок отримує швидшу перевірку (окрім небезпечних видів).
- Скарга («не той гриб», «образливий опис») → повторна перевірка; підтверджена скарга —
  −50 балів автору.

### 18.5 Місце публічної точки
- Точні координати бачить **лише автор** (і учасники поїздки, якщо він поширив точку).
- Іншим публічна точка показується **з похибкою 300–500 м** (за замовчуванням ~400 м),
  **у межах того самого полігона лісу**; поза лісом на карті — точно, без зміщення (ADR-019 §19.1, §19.6).
  Зсув **стабільний для кожної точки** (детермінований від її id), щоб повторні запити не
  дозволяли «усереднити» справжнє місце.
- Прогноз і теплова карта (B3.5, B3.9) використовують точні координати лише на сервері.

### 18.6 Технічні наслідки
- Міграція: `pick_type` — тільки `private` / `public`; наявні `friends` → `private`;
  `friendships` не створюється; B3.6 видалено.
- `mushroom_picks`: `species_id` (FK на довідник, NULL = «Не знаю»), `description`,
  `ai_check JSONB`, `twin_alert`, `verification_status`, `display_point` (зсунута точка).
- `pick_reviews` (pick_id, reviewer_id, verdict `yes|no|other_species`, other_species_id,
  weight, created_at), унікально на (pick, reviewer); `pick_reports` (скарги).
- API: `GET v1-picks/map` віддає для чужих точок тільки `display_point`; `GET v1-picks/review-queue`,
  `POST v1-picks/{id}/review`, `POST v1-picks/{id}/report`.
- Клієнт: тільки камера (`image_picker` / `camera` без галереї), один кадр.

## ADR-019: Ліс у тук-туці, голоси за тип полігона, підтвердження відповіддю і масштаб

**Дата:** 2026-11-12, доповнено 2026-11-13 · **Статус:** ✅ Прийнято · **Змінює:** ADR-011
(ліміт приватних — на тиждень), ADR-012 №3 (бали за приватну точку — на тиждень), ADR-013 §13.5
(ліміти публічних free — на тиждень), ADR-014 (§19.9), ADR-018 §18.3 (форма), §18.4 шар 2
(перевірка — відповіддю знахідкою, не окремою групою перевіряльників), §18.5 (зміщення в
межах лісу). **Уточнює:** ADR-015 §15.5 (пріоритет джерел типу лісу).

**Навіщо.** Точка, де людина знайшла гриб, — найточніше джерело про ліс (точніше за OSM і
супутник). Збираємо це без перемальовування карти, без шуму в аналізі й так, щоб система
витримала десятки тисяч користувачів.

### 19.1 Точка в лісі і поза лісом
1. Телефон визначає за файлом лісів області (як ліс у ділянці аналізу, ADR-015 §15.4.6), чи
   точка **в межах полігона лісу** (допуск ~30 м — похибка GPS і спрощення контурів). Якщо так —
   надсилає з точкою **id полігона** і **фрагмент його контуру в квадраті ~1×1 км** навколо
   точки (для зміщення, §19.6). У БД сервера ліси є не для всіх областей.
2. **Поза лісом на карті** (луки, поля, ліси, яких немає в OSM) тук-тук теж можна створити —
   приватний і публічний:
   - **приватний** — як звичайно (його бачить лише автор);
   - **публічний** — показується **точно за геолокацією, без зміщення**. Перед публікацією
     автор бачить попередження: «Тут немає лісу на карті — точку побачать усі точно, без
     зміщення»;
   - голосу за тип лісу така точка не дає (полігона немає); решта правил публічних точок
     (лише їстівні види, підтвердження відповіддю) — без змін.
3. Збірка файлу лісів повторно перевіряє «точка в полігоні» для голосів (§19.4): голос поза
   полігоном не рахується, хоч би що надіслав клієнт.

### 19.2 Форма тук-тука
1. **Вид гриба — лише зі списку довідника.**
   - **Публічний тук-тук — у списку лише їстівні види.** Мухомори, бліда поганка, жовчний гриб
     тощо вибрати неможливо; сервер це теж перевіряє (підроблений запит → відмова).
   - **Приватний — повний список** (зокрема отруйні й «Не знаю, що це»): його бачить лише автор.
2. **«В якому лісі» — обов'язково.** За породами: сосновий, ялиновий, дубовий, березовий,
   осиковий, вільховий, грабовий, буковий тощо — **1 або 2 породи** (дві = мішаний із цих
   порід). Застосунок підставляє підказку з карти (тип полігона під точкою), людина
   підтверджує або змінює. «Хвойний / листяний за супутником» — лише підказка.
3. **«Під яким деревом» — за бажанням.** За тип полігона не голосує (один дуб у бору не робить
   бір дібровою) — лише аналіз і статистика.
4. Опис — вільний текст (ADR-018 §18.3.4).

### 19.3 Знімок обставин знахідки — автоматично, у фоні
1. З кожною точкою зберігаються: дата й час **зйомки**, висота, погода (опади й температура за
   2–3 тижні до знахідки, вологість ґрунту), ліс (що показувала карта і звідки тип + відповідь
   людини), дерево, вид.
2. Погоду **не** запитуємо під час створення точки (обмежений час Edge Functions). Точка
   створюється одразу, а **фонове завдання** (pg_cron, кожні кілька хвилин) дозаповнює погоду
   пачками з повторами при збоях; сусідні точки однієї доби — одним запитом на клітинку сітки.
   Джерело — Open-Meteo: останні ~3 місяці — основний API (`past_days`), старше — архів
   (оновлюється із затримкою ~5 днів).
3. **Приватна точка:** у спільні дані йдуть лише **дата, час і погода** (без координат). Ліс і
   дерево — у картці точки, статистиці й аналізі **самого автора** («твої білі — переважно під
   дубом»; знахідки автора в його ділянці аналізу) і голос за тип полігона (§19.4).
4. **Публічна точка:** усе — у спільні дані; відповіді з породами — мітки для перенавчання
   супутникової моделі типу лісу (§19.8).

### 19.4 Голоси за тип полігона
1. Голос дає кожен тук-тук із перевіреним фото в межах полігона: приватний (успішна
   EXIF-перевірка), публічний і відповідь на публічний (§19.5). Голос — породи з поля «В якому
   лісі».
2. Рахуються голоси **різних людей** (кілька точок однієї людини в полігоні — один голос).
   Голоси, старші за **5 років**, і голоси до дати вирубки (§19.7) не рахуються.
3. **Скільки голосів потрібно:**
   - полігон **до 10 км²** — порода підтверджена, якщо за неї **≥ 3 голоси**;
   - полігон **понад 10 км²** — тип змінюється, коли є **≥ 10 голосів з різних ділянок**:
     точки щонайменше за **1 км** одна від одної (з однієї ділянки 1×1 км — один голос), щоб
     одна галявина не змінювала тип цілого масиву.
4. **Підпис за часткою голосів** (однаково для малих і великих полігонів):
   - одна порода → «Сосновий ліс»;
   - головна порода **≥ 70%** голосів → «Сосновий з домішкою дуба» (напр. 9 «сосна» + 1 «дуб»);
   - головна порода **< 70%** → «Мішаний: сосна, дуб» (за кількістю голосів);
   - порода з часткою **< 10%** у підпис не йде (напр. 20 «сосна» + 1 «дуб» → «Сосновий ліс»).
5. **Полігони не перемальовуємо й не ділимо** — змінюється лише підпис. Ліс у конкретному місці
   видно в картці публічного тук-тука («Ліс: дубовий · під дубом»). Нових латок і меж від
   користувачів на карті немає. Ділити величезні масиви за супутниковою картою — пізніше, якщо знадобиться.
6. Пріоритет джерел типу: **за даними грибників** > порода з OSM > хвойний/листяний з OSM >
   назва урочища ≈ супутник. Підпис джерела у визначнику: «За даними грибників» — без кількості
   голосів і без позначки, приватні вони чи публічні.
7. Тип із голосів застосовується під час перебудови файлу лісів області (не миттєво).
   Координати приватних точок не потрапляють у файли, артефакти й логи збірки — у файлі лише
   підсумковий тип полігона. Від виду гриба голос не залежить: мухомор так само показує березу.

### 19.5 Публічні точки: сірі → підтверджені відповіддю знахідкою
**Окремої групи «перевіряльників» немає** (замінює ADR-018 §18.4, шар 2).
1. Публічний тук-тук **одразу видно всім на карті сірим** («Перевіряється»).
2. **Підтверджена (зелена)** — коли інший користувач відповів на неї **своєю перевіреною
   знахідкою: фото з камери + повідомлення**. Зірок і оцінок немає.
3. Відповідати може лише **Лісовик і вище** (як і створювати публічні точки, ADR-013); відповідь
   входить у тижневий ліміт публічних точок (§19.10) і проходить ті самі перевірки (їстівний
   вид, фото, ліс).
4. Умови відповіді: фото камерою застосунку в межах **~200 м** від точки, від іншої людини (себе —
   не можна; взаємні підтвердження тих самих двох людей обмежені). **Вікна в днях немає** —
   знахідка на тому ж місці через місяць чи рік лише підтверджує, що місце плодоносить.
5. На точці видно: «Підтвердили N грибників, останнє — <дата>». Негативних оцінок немає: точка
   без підтверджень згасає з часом.
6. Точка з `twin_alert` (модель на телефоні бачить отруйного двійника, ADR-018) автоматично
   зеленою не стає — потрібні щонайменше 2 відповіді, і на точці лишається попередження.
7. **Бали:** тому, хто підтвердив, — ADR-012 №4 (+3); **автору — фіксовано +2 за кожне
   підтвердження, не більше 10 на добу.**
8. Повідомлення публічне: обмеження довжини, фільтр лайки, телефонів і посилань, «Поскаржитися».

### 19.6 Зміщення публічної точки — у межах лісу
1. Іншим публічна точка **в лісі** показується зі зсувом 300–500 м (ADR-018 §18.5, стабільний
   від id), але **зсунута точка лишається в тому самому полігоні лісу** — на карті вона ніколи
   не «виходить у поле». Публічна точка **поза лісом** — без зміщення (§19.1).
2. Сервер рахує `display_point` у фрагменті контуру з §19.1: шукає детерміновану точку на
   відстані 300–500 м усередині полігона. Якщо ліс замалий для такого зсуву — береться
   найдальша можлива точка всередині полігона (менший зсув; у малому гаї точка лишається в гаї).

### 19.7 Вирубки й згарища
1. Кнопка «Тут вирубка / згарище» у визначнику лісу і на точці. Це **не голос за тип**, а сигнал.
2. **3 скарги різних людей** або рішення модератора → полігон отримує позначку «Вирубка (за
   повідомленнями)», голоси до дати вирубки не рахуються.
3. Під час щорічного перерахунку супутникової карти підозрілі місця (різке падіння зелені між
   роками) підсвічуються автоматично.

### 19.8 Супутникова модель
Публічні відповіді з породами — мітки для перенавчання моделі типу лісу (раз на рік, згодом
частіше). Межі хвойного / листяного уточнюються по всій Україні, з часом — можливо, до порід.
Приватні відповіді в навчання не йдуть.

### 19.9 «Не знайшов» не використовуємо
Відповіді «не знайшов» не йдуть ні в голоси, ні в навчання й калібрування прогнозу: людина могла
поставити «не знайшов», а потім знайти поляну за 200 м. **Уточнення ADR-014:** відповідь «Ні» на
«Знайшли?» лишається для користувача (щоденник, бали за ADR-014), але в `calibration_log` і
навчання не потрапляє.

### 19.10 Масштаб: ліміти і фото
Розрахунок для 10 000 користувачів: з оригіналами фото (~2 МБ) і 5 приватними на добу — ~100 ГБ
фото на добу (~3 ТБ на місяць). Дорого коштують сховище й трафік фото, не рядки в БД
(десятки тисяч рядків на добу Postgres тримає без проблем). Тому:

**Приватні точки — ліміт на кількість одночасно, а не на період** (рішення PO 2026-11-13):

| Ліміт | Було | Стало |
|---|---|---|
| Приватні, безкоштовно (і гість) | 5 на добу (ADR-011) | **до 5 одночасно** — щоб додати нову, треба видалити стару |
| Приватні, Pro | без ліміту | **до 15 одночасно** |
| Нових приватних (проти «створив → видалив → створив») | — | **до 10 на тиждень** |
| Бали за приватну точку з EXIF (ADR-012 №3) | +1, до 5 на добу | **+1, до 5 на тиждень** |
| Публічні, Лісовик (free) | 5 на добу (ADR-013) | **7 на тиждень** |
| Публічні, Хранитель лісу (free) | 10 на добу | **15 на тиждень** |
| Відповіді-знахідки | — | у ліміті публічних |

- Тиждень — 7 днів, що минули (ковзне вікно), за київським часом.
- Застосунок знає кількість точок і попереджає **до знімка**: «У вас 5 з 5 — видаліть одну, щоб
  додати нову» (і в лісі без мережі). Точки з офлайн-черги понад ліміт сервер відхиляє з тим
  самим повідомленням (ADR-011).
- **Закінчився Pro, а точок більше 5:** нічого не видаляється, усі точки видно; нову можна
  додати, лише коли їх стане менше 5.
- **Видалення приватної точки:** зникають точка, мініатюра, ліс і дерево, **голос за тип лісу**
  (видалив — значить нема). Погода й час, уже записані **без координат** у спільні дані,
  лишаються — вони знеособлені.
- Ліміти публічних точок у Pro (ADR-013 §13.5) — окремим рішенням разом із B6.3.

**Фото:**
1. **Приватні точки:** оригінал лишається **лише на телефоні**. На сервер фото йде для перевірки
   EXIF; після неї сервер **видаляє оригінал і зберігає мініатюру ~30 КБ** (картка точки на
   іншому пристрої).
2. **Публічні точки:** телефон стискає фото до ~1280 px (~200 КБ) і робить мініатюру ~20 КБ. На
   карті й у списках — лише мініатюри, повне фото — коли людина відкрила точку.
3. Повне фото публічної точки, яку ніхто не підтвердив, видаляється після сезону; мініатюра лишається.
4. Карта завантажує точки лише для видимої області, з групуванням при віддаленні; фото — через
   CDN Supabase Storage і кеш на телефоні. Розрахунок — під сезонний пік (вересень–жовтень).

Очікувано: ~1 ГБ фото на добу в пік замість ~100 ГБ; приватні мініатюри обмежені назавжди
(10 000 користувачів × 5 точок × ~30 КБ ≈ 1,5 ГБ).

**Задачі (порядок):**
1. Ліміти (приватні — одночасно 5 / 15, нових ≤ 10 на тиждень; публічні — на тиждень) і фото:
   стискання, мініатюри, видалення оригіналів приватних; видалення приватної точки.
2. Форма тук-тука: ліс / поза лісом (§19.1), їстівні види для публічних, породи й дерево.
3. Знімок обставин знахідки у фоні (§19.3).
4. Картка точки (ліс, дерево), статистика автора, знахідки автора в аналізі ділянки.
5. Публічні точки: сірі → підтвердження відповіддю, бали автору (§19.5); зміщення в межах лісу (§19.6).
6. Голоси → тип полігона у збірці файлів лісів (§19.4); скарги «вирубка» (§19.7).
7. Перенавчання супутникової моделі на публічних мітках; «Ні» — поза калібруванням (§19.9).

## ADR-020: Офлайн карта області (без серверних плиток)

**Дата:** 2026-11-13, оновлено 2026-11-14 · **Статус:** ✅ Прийнято (рішення PO)

**Навіщо.** Підкладка бралася з публічного сервера плиток `tile.openstreetmap.org`: його
правила забороняють застосункам масове й офлайн-використання, швидкість не гарантована, а без
інтернету (у лісі) карта порожня.

1. **Серверної карти в застосунку немає.** Карта показується лише з **офлайн карти області**.
   Поки її не завантажено, на вкладці «Карта» по центру екрана — лише «Офлайн карта ·
   Завантажити · ≈ N МБ»; карта й усі кнопки (аналіз, тук-тук, приватні точки) з'являються
   після завантаження. Немає мережі — «Потрібен інтернет, щоб завантажити офлайн карту»;
   для області карти ще немає — «ще готується».
2. **Карту області будуємо самі** з вивантаження OpenStreetMap (Geofabrik), як і ліси:
   Planetiler, схема OpenMapTiles, один файл **PMTiles** на область, z0–14 (далі —
   наближення без нових даних). Без будівель, номерів будинків, POI й аеропортів; назви —
   `name:uk`. Workflow «Basemap» (`all` — усі області паралельно), реліз `basemap-data`.
   Ліцензія — ODbL: підпис «© OpenStreetMap contributors».
